## 0. 我理解的目標與問題（用自己的話）

**目標**：把兩支「只認得一場比賽」的 App，變成一支「認得很多場比賽」的 App。
引擎只寫一次，每場比賽的資料裝成一個「賽事包」放進去就能跑。

**要解決的問題**：

1. 現在每場比賽都把路線、關門、水站「寫死」在程式裡 → 加一場就要複製一整支 App，改一個功能要改兩份。
2. 兩場比賽的設定和紀錄若放在同一支 App，可能互相覆蓋（例如京都的分段蓋掉日月潭的）。
3. 日月潭當天到終點後一直報「不在賽道上」→ App 不知道「你已經跑完了」。
4. 京都 2027/2/21 不能冒險 → 舊 Kyoto-Run APK 保留，新 App 用不同套件名稱並存。

```
現在                                   M1 之後
───────────────────────                ─────────────────────────────────
Kyoto-Run   = 引擎 + 京都資料(寫死)       Run-Navigator = 一套引擎
MSL-run     = 引擎 + 日月潭資料(寫死)                      │
  （九成程式重複，改功能要改兩次）                         ├─ 賽事包：京都 2027
                                                       ├─ 賽事包：日月潭 2026
                                                       └─ （以後）匯入的新賽事
```

## 1. 賽事包格式

### 1.1 一個賽事包長什麼樣子

一場比賽 = 一個資料夾。裡面只有資料，沒有程式。

```
app/src/main/assets/races/
├─ kyoto-2027/
│   ├─ race.json      ← 人寫的：日期、地標、區段、關門、水站、膠…
│   ├─ route.gpx      ← 原始路線（座標＋海拔）
│   ├─ route.json     ← 機器產生：縮放到官方距離、每 ~100 m 一點
│   └─ map.png        ← 機器產生：離線地圖
└─ sunmoonlake-29k-2026/
    └─ （同上）
```

為什麼要從 `RouteData.java` 改成 `route.json`：
現在路線是編譯進 Java 的；以後要「匯入賽事包」，手機上沒辦法重新編譯，
所以路線一定要變成 App 執行時才讀的資料檔。畫面（JS）和背景服務（Java）讀同一份。

```
          tools/build_route.py
route.gpx ─────────────────────▶ route.json ──┬──▶ 畫面 index.html（JS）
                                               └──▶ 背景 GpsService（Java）
race.json ─────────────────────────────────────┴──▶ （兩邊同一份，不會不一致）
```

### 1.2 `race.json` 欄位（以京都為例，節錄）

```jsonc
{
  "format": 1,                       // 格式版本，以後改格式時用來相容舊包
  "id": "kyoto-2027",                // 唯一 id：存檔、紀錄都用它分開
  "name": "京都馬拉松 2027",
  "short": "京都 42K",
  "kind": "race",                    // race＝賽事；route＝練習路線（M3 匯入用）

  "time": {
    "tz": "Asia/Tokyo",              // 賽事當地時區，畫面時間都以此顯示
    "gun": "2027-02-21T09:00:00+09:00",
    "limit_min": 360                 // 總時限（分）
  },
  "distance_m": 42195,               // 官方距離；route.json 會縮放到這個長度

  "route": {
    "source": "ibuki.run（sagara-221/FutureRun）",
    "out_and_back": true             // 有折返段：提醒驗證對位（對位算法本身在引擎，京都邏輯原樣保留）
  },

  "landmarks": [                     // = 現在的 LM
    { "n": "關1", "name": "清滝道三条（嵐山）", "km": 6.1, "cut": true,
      "note": "第 1 關門 10:02。過了接嵐山高架緩上。" }
  ],
  "sections": [                      // = 現在的 SEC（A 點 → B 點）
    { "a": 6.1, "b": 9.1, "from": "清滝道三条", "to": "一条山越（第2關）",
      "terr": "嵐山高架、廣澤池，緩上 +10 m", "act": "關門最緊的一段，小步維持不要停" }
  ],
  "cutoffs": [                       // = 現在的 CUT，以「鳴槍後分鐘」計
    { "km": 6.1, "name": "清滝道三条", "min": 62 }
  ],
  "aid": {                           // = 現在的 AID＋AID_LAB
    "labels": { "w": "水", "f": "食" },
    "stations": [
      { "n": 6, "km": 17.6, "name": "御薗橋西詰北", "s": "wf", "food": "都こんぶ・豆パン" },
      { "n": 2, "km": 7.9, "name": "京都工繊大（嵯峨）", "s": "w", "est": true }
    ]
  },
  "gels": [ { "km": 7.9, "label": "#1", "aid": 2 } ],

  "plan": {                          // 配速計畫怎麼算（見 1.3）
    "model": "grade",
    "default_target_min": 330,
    "crowd": [ { "to_km": 3, "x": 1.05 }, { "to_km": 6.1, "x": 1.03 } ],
    "cut_buffer_min": { "first_n": 3, "early": 4, "later": 6 }   // 前 3 關留 4 分、之後留 6 分
  },

  "finish": { "radius_m": 100, "min_frac": 0.98 },   // 完賽判定（M1 新功能）

  "start_delay_options": [0, 1, 4, 10, 15, 18],        // 起跑延遲選項（分）
  "schedule": {                      // 接下來幾年的報名與比賽日期（賽事準備頁卡片＋首頁卡片一行）
    "rule": "每年 2 月第 3 個週日；報名在前一年 7 月中開放",   // 往年慣例，推估的根據
    "checked": "2026-11-03",         // 最後查證日
    "items": [
      { "year": 2027, "race": "2027-02-21", "race_est": false,      // false＝官方、true＝預估
        "entry": "國內抽籤 2026/7/16–8/31…", "entry_short": "2026/7/16–9/30", "entry_est": false,
        "open": "2026-07-16", "close": "2026-09-30",              // 有確切日期才寫：畫面顯示 報名中／已截止
        "src": [["京都市 2026/7/8 募集新聞稿", "https://…"]] },    // 官方資料一定要附來源
      { "year": 2028, "race": "2028-02-20", "race_est": true,
        "entry": "約 2027/7 中旬開放…", "entry_short": "約 2027/7 中旬開放", "entry_est": true,
        "basis": "2 月第 3 個週日＋2027 屆的募集時程" }            // 預估一定要寫推估依據
    ],
    "note": "住台灣報海外名額：先到先得…"
  },
  "sources": [ { "item": "關門", "src": "2026 官方", "trust": "高" } ]
}
```

`schedule` 的規則由 `tools/build_races.py` 檢查：官方要有 `src`、預估要有 `basis`、比賽日要是週日、跟 `time.gun` 同一年時日期要一致。官方公布新一屆時，把該年的 `*_est` 改成 `false`、補上 `src`，再往後加一年。

日月潭的包欄位完全一樣，只是數字不同。

### 1.3 兩場比賽「配速計畫」算法不同，怎麼處理

```
京都（model: "grade"）                    日月潭（model: "rows"）
────────────────────────                 ────────────────────────
依坡度自動算每 100 m 的權重                每個區段直接寫一個基準配速
× 起跑擁擠 × 後段疲勞                     （手調過，例如 C坡最陡 13:00/km）
→ 再依關門自動前移（關門保護）              → 等比例縮放到目標時間
```

**我的建議**：引擎兩種都支援，日月潭沿用它原本的手調配速（`rows`）。
理由：日月潭已經跑完，回顧時「計畫 vs 實際」要跟當天 App 顯示的一模一樣才有意義。
新賽事預設用京都的 `grade`（不用手調，只要有海拔就能算）。

### 1.4 存檔怎麼隔離

```
手機存檔（SharedPreferences ＋ 網頁 localStorage，同一套命名）
├─ pref.*                  個人偏好（全 App 共用）
│    語音、震動、每 1K 報告、停下 10 秒報告、主題、跑者名稱
├─ race.kyoto-2027.*       京都自己的一格
│    目標時間、起跑延遲、起跑時間、分段紀錄、完賽狀態
├─ race.sunmoonlake-29k-2026.*
│    （同上，互不影響）
└─ active                  目前正在定位的是哪一場（同時只有一場）
```

舊日月潭 App 的分段紀錄「匯入」排在 M2（紀錄功能）；M1 先把格子留好。

## 4. 讀程式時發現、要注意的地方

- 日月潭 repo 沒有原始 GPX，只有每 100 m 一點的 `RouteData.java`（來源 RideWithGPS #38261247）。
  會從這些點反產生 `route.gpx`，精度和現在 App 一樣。
- 日月潭里程是用 `(點數−1)×100 m` 算，京都是縮放到 42.195 km；新引擎統一用 `distance_m`。
- 京都的關門時刻目前是 2026 官方值；1 月的排程更新要改成更新 `races/kyoto-2027/race.json`。

**③ 怎麼跑自測（發版保護）**

```
python3 tools/build_races.py --check          # ① 賽事包檢查，races.js 必須是最新
node tools/selftest.js                        # ② 無頭瀏覽器：首頁、節拍器、每個賽事包示範跑完全程＋300 px 量字寬
#   需要 playwright 與 chromium。本機若是全域安裝：
#   NODE_PATH=$(npm root -g) node tools/selftest.js
#   指定瀏覽器：CHROME_PATH=/path/to/chrome node tools/selftest.js
# ③ JVM 對位模擬與 ④ 編 APK 只在 GitHub Actions 跑（指令在 .github/workflows/build.yml）
```

- 自測輸出在 `build/selftest/`（截圖、`course-<id>.json`），這個資料夾不進版控。
- CI 會安裝 `fonts-noto-cjk` 來量字寬；本機沒有這套字型時，300 px 的結果可能跟 CI 略有出入，以 CI 為準。
- 本機編不了 Android（下載不到 SDK），APK 一律看 Actions 結果。

**④ PR 規則**

- 從 `main` 開新分支（`claude/...`），開 PR。**不要從 PR #6 的分支接著做**（原因見 ⑤）。
- PR 會自動編「測試版 APK」（套件名稱 `zl.runnav.app.debug`，可跟正式版同時裝），在 Actions 頁面最下方的 Artifacts 下載，請使用者試裝。
- 合併到 `main` 才會發佈正式版到 Releases，所以**合併一律由使用者決定**。
- 每個 PR 都要改 `app/build.gradle` 的 `versionCode`（+1）與 `versionName`，並在本檔「版本紀錄」加一行。
- 一個 PR 只做一件事。會碰到比賽日程式（配速計畫、`Course`、`GpsService`、通知列）的改動，要單獨一個 PR。

**⑤ 不可自行合併 PR #6**

PR #6（分支 `claude/project-thread-suscot`，v0.8：訓練紀錄、Garmin／Strava CSV 匯入）CI 已通過，但**使用者決定先保留、不推正式版**，目前是 draft。沒有使用者明確說「合併」，不可以合併、不可以改成 ready、也不可以把它的程式碼帶進別的 PR。

## 目的與背景

把「日月潭 29K」和「京都馬拉松 42K」兩支賽道定位 App 整合成一支 **Run-Navigator**：一套共用引擎，加上多個互相隔離的賽事包，再補上跑步紀錄、自由跑與匯入練習路線。

- **為什麼整合**：兩支 App 有九成程式重複（GPS 對位、語音、通知列、畫面框架），每次改功能都要改兩份。
- **最大的限制**：京都馬拉松 2027/2/21 不能冒險。舊的 `Kyoto-Run` APK 要保留到新 App 通過一次實跑測試才退役。
- **使用者**：新手跑者（日月潭 29K 是第一場長距離，2026/11/1 已完賽），用 Android（Pixel 7／8 Pro），跑步時不看手機，只有停下來才瞄一眼。

**資料流**：畫面算配速計畫 → `setCourse` 存進這一場的儲存格 → 背景服務讀取 → GPS 對位 → 語音、通知列、狀態推回畫面。

**儲存規則（很重要，新欄位一律照這個做）**

```
個人偏好（全 App 共用）              賽事參數（每場各自一格）
────────────────────────          ──────────────────────────────
APK：SharedPreferences "pref"      APK：SharedPreferences "race_<id>"
網頁：localStorage rn_<k>          網頁：localStorage rn_<id>.<k>

name vib tts kmv stopv keepOn       target（目標，分鐘） delay（起跑延遲，分鐘）
theme win                           start（起跑時刻） splits（分段） finished（完賽）
mbpm macc msnd mvib mdur（節拍器）   raceBpm（比賽步頻） regCat（報名組別）
                                    course（畫面算好的計畫，給背景服務）
另外：pref 裡的 active ＝ 目前正在定位的那一場（同時只有一場）
PR #6 另有獨立的 "store"（網頁 rn_tlog、rn_tgoal）：訓練紀錄與月跑量目標
```

寫入走 `gset(id, k, v)`（首頁）或 `pset(k, v)`（賽事頁）；讀取走 `racePrefs(id)`。
**新增一個欄位要改 4 個地方，少一個就會「存得進去、讀不出來」：**

1. `index.html` 的 `SHARED`（如果是共用偏好）。
2. `index.html` 的 `racePrefs()` 網頁分支：把新欄位讀出來放進回傳物件。
3. `MainActivity.java` 的 `SHARED`（要跟 1 一樣）與 `getPrefs()`：把新欄位 `put` 進 JSON。
4. `MainActivity.java` 的 `setPref()`：整數欄位要加進 `putInt` 那一行的 `case`；字串與 JSON 字串走預設的 `putString`。

自測模式（`&selftest`）下 `gset`／`pset` 不會寫入，所以要測新欄位時，請用網址參數帶值（下面三份規格都有寫）。

## 定案規格

一支 APK、一套引擎、多個賽事包；每場賽事的資料與參數各自獨立，個人偏好全 App 共用，同時只有一場在定位。

**共用與隔離**

| 類別 | 項目 | 範圍 |
| --- | --- | --- |
| 個人偏好 | 語音、震動、每 1K 報告、停下 10 秒報告、亮暗主題、跑者名稱、節拍器設定 | 全 App 共用 |
| 賽事參數 | 目標時間、預估起跑延遲、起跑時間、分段紀錄、完賽狀態、比賽步頻 | 每場各自 |
| 定位 | 背景 GPS 服務 | 同時只有一場；開始新的一場前先請使用者停止另一場 |
| 發版保護 | GitHub Actions 每次編譯前，用示範模式把每場賽事都跑一遍 | 任一場出錯就不發佈 |

**使用者的決定（2026/11/2 討論）**

1. 日月潭：回顧紀錄＋明年再跑＋當練習路線，全部都要。
2. 新賽事：要能自己匯入賽事包（GPX＋賽事設定檔）。
3. 不互相影響：分段紀錄、每場設定、程式更新、比賽日不誤開，四項都要。
4. 打開 App：每次先出現賽事／路線清單，手動選。
5. 設定：個人偏好共用、賽事參數各自獨立（上表）。
6. 舊 APK：三支並存，新 App 套件名稱不同（`zl.runnav.app`，舊的是 `tw.kyoto42k.locator`、`tw.sml29k.locator`），不會蓋掉舊的；確定沒問題再刪。
7. 練習：要「自由跑」（無路線，只報距離與配速），也要從 Google My Maps（KML）或其他含座標與高度的 GPX 匯入練習路線。
8. 網頁版：只做測試與分享，比賽一律用 APK。

**使用者後來的決定（2026/11/15）**

9. PR #6（訓練紀錄 v0.8）先保留，不推正式版。

## UI/UX 原則（從程式碼歸納，新畫面請照做）

使用情境只有兩種：**跑步中（不看手機）**與**停下來瞄一眼（單手、可能在大太陽下、可能很喘）**。

| 原則 | 程式裡怎麼做 | 新功能要注意 |
| --- | --- | --- |
| 跑步時不看手機 | 重要資訊都有語音＋震動；鎖屏通知列有對照圖 | 任何「跑步中才有用」的資訊，一定要有語音版本，不能只做畫面 |
| 瞄一眼就懂 | 賽道頁最上面只有三樣：里程（最大 72 px）、對照計畫、關門餘裕；策略用大字 | 一張卡只回答一個問題；最重要的數字放最大 |

| 危險動作按兩下 | `twoTap()`：「我完賽了」「停止定位」第一次按會變成「再按一次：…」，3 秒後復原 | 清除、停止、覆蓋類的動作都用 `twoTap` |

| 深色優先、亮色可切 | 深色是預設（OLED 省電）；跟隨系統 `prefers-color-scheme`，也可手動切（`data-theme`）；顏色一律用 CSS 變數 | 不寫死顏色；通知列的圖（`Strip`）自帶深色底 |

### ① 備賽週期計畫

**要解決的問題**
使用者是新手，知道比賽日，但不知道「這週該跑多少、長跑跑多遠、什麼時候該開始減量」。新手最常見的兩個錯：太晚才拉長跑、賽前兩週還在加量。App 知道比賽日與目標配速，可以直接往回推一份保守的課表。

**放在哪裡**
賽事準備頁（`pgPrep`）。位置隨「離比賽多久」改變，因為越接近比賽，「開始定位」越重要：

```

────────────────────                ────────────────────             ──────────
倒數卡                                倒數卡                             不顯示
這一場的參數                           這一場的參數
▶ 備賽計畫卡（展開本週）                關門提醒、計畫表／地圖
關門提醒、計畫表／地圖                   開始定位（比賽）
開始定位、練習模擬                      ▶ 備賽計畫卡（收成一行）

```

**線框圖（寬 300 px 也要放得下）**

還沒設定時：

```
│ 基礎→強化→巔峰→減量          │
│ ████░░░░░░░░░░ ▲你在這        │
│                            │

```

- 四階段進度條：4 段顏色（基礎藍 `--aid`、強化黃 `--warn`、巔峰紫 `--plan`、減量綠 `--ok`），寬度依週數比例，用 `▲` 標出本週。
- 「看完整 14 週」展開成表格：週次｜日期｜階段｜週跑量｜長跑；恢復週標「恢復」。表格外層 `overflow-x:auto`。
- 收成一行時：`🗓 減量期・倒數第 1 週・本週 17 km（不含比賽）`。

**計算規則**

輸入：比賽日、距離 `D`（km，`R.distance_m / 1000`）、目標 `target`（分鐘，用 `S.target`；②完成後用「理想」）、目前週跑量 `wk0`（km）、最近 4 週最長一次 `long0`（km）。

第 1 步：算週次。一週的最後一天＝比賽的星期幾（比賽都在週日，所以一週是週一到週日）。

```
d ＝ 比賽日 − 今天（天數，比賽當天 d＝0）
W ＝ floor(d / 7) + 1          ← 「倒數第 W 週」，比賽那一週是 W＝1
排課表那天，如果這一週只剩 2 天以內（d mod 7 ≤ 1），就從下一週開始：N ＝ W − 1；否則 N ＝ W
N 最多取 24；超過時顯示「距備賽期還有 x 週，先維持目前跑量」，到倒數第 24 週再開始
```

例：京都 2027/2/21（日），今天 2026/11/15（日）→ d＝98，W＝15，但這一週只剩今天 → N＝14，從 11/16（一）開始，剛好 14 個整週。

第 2 步：分四階段（從比賽日往回排）。

```
減量 T ＝ D ≥ 30 km ? 3 : 2          （不超過 N）
巔峰 P ＝ N ≥ 12 ? 3 : N ≥ 8 ? 2 : 1  （不超過 N − T）
剩下 rest ＝ N − T − P
強化 B ＝ ceil(rest / 2)
基礎 A ＝ rest − B
```

| N | D | 基礎 | 強化 | 巔峰 | 減量 |
| --- | --- | --- | --- | --- | --- |
| 14 | 全馬 | 4 | 4 | 3 | 3 |
| 20 | 全馬 | 7 | 7 | 3 | 3 |
| 10 | 半馬 | 3 | 3 | 2 | 2 |
| 6 | 全馬 | 1 | 1 | 1 | 3 |
| 2 | 全馬 | 0 | 0 | 0 | 2 |

N ≤ 3 時只有減量，卡片要明說：「離比賽太近，現在加量只會累，照減量跑就好。」

第 3 步：長跑上限 `Lmax`。新手的長跑用「時間」封頂，不用距離硬撐：最長一次不超過 3 小時 30 分。

```
目標配速 MP ＝ target / D                 （分/km）
輕鬆配速 easy ＝ MP × 1.10
距離上限 lcap ＝ D ≥ 40 ? 30 : D ≥ 25 ? round(0.8 × D) : round(0.85 × D)
Lmax ＝ max(long0, min(lcap, floor(210 / easy)))
```

例：京都目標 5:30 → MP＝330 ÷ 42.195＝7.82 分/km（7:49）；easy＝8.60 分/km（8:36）；210 ÷ 8.60＝24.4 → 24 km；lcap＝30 → `Lmax＝24 km`。
（目標 4:30 的人會算出 29 km；半馬 `lcap＝18`；日月潭 28.8K `lcap＝23`。）

第 4 步：每週跑量與長跑。前 `N − T` 週是「加量期」，其中每逢第 4 週是恢復週（加量期的最後一週除外，那一週要跑最長的長跑）。

```
k ＝ 加量期裡「不是恢復週」的週數 − 1
週跑量高峰 wkPeak ＝ max(wk0, min(wk0 × 1.10^k, Lmax × 2, 60))
        （每週最多 +10%；長跑不超過週跑量的一半；新手上限 60 km）
g ＝ (wkPeak / wk0)^(1/k)                 ← 每週成長倍率，一定 ≤ 1.10
第 j 個非恢復週（j 從 0 起）：週跑量 ＝ wk0 × g^j
                             長跑   ＝ long0 + (Lmax − long0) × j / k
恢復週：週跑量 ＝ 上一週 × 0.8；長跑 ＝ 上一週 × 0.7
減量（全馬）：倒數第 3 週 ＝ wkPeak × 0.75、長跑 Lmax × 0.65
             倒數第 2 週 ＝ wkPeak × 0.55、長跑 Lmax × 0.45
             倒數第 1 週 ＝ wkPeak × 0.35（不含比賽），長跑欄顯示「比賽」
減量（半馬等）：倒數第 2 週 ＝ wkPeak × 0.70、長跑 Lmax × 0.60；倒數第 1 週 ＝ wkPeak × 0.45
所有 km 四捨五入到整數
```

### ② 目標時間區間（理想／保底）

**要解決的問題**
現在只有一個目標（例如 5:30）。跑步中只會聽到「比計畫慢 2 分 10 秒」，新手一聽到「慢」就慌、就亂追。實際上跑者心裡有兩條線：「順的話 5:30，最差 5:35 也可以」。App 應該能說出「還在區間內，照現在的節奏跑」，只有掉出保底才提醒。

**名詞**

| 名稱 | 欄位 | 意思 |
| --- | --- | --- |
| 理想 | `target`（現有欄位，意思不變） | 比較快的那條線。配速計畫、關門保護、「比計畫快／慢」都照它算，跟現在一樣 |
| 保底 | `target2`（新欄位，可以不設） | 比較慢的那條線，但仍然過得了每一個關門 |

**安全設計（這一節最重要）**

現在的流程：

```
S.target, S.delay ──▶ buildPlan() ──▶ PC[]（每個路線點的累積分鐘，已做關門保護）
                                        ├─▶ 畫面：planMin()、planKm()、計畫表、對照線
                                        └─▶ coursePayload().plan ──setCourse──▶ Course.plan
                                                                    └▶ GpsService 語音、通知列、Strip
```

改完之後：

```
S.target  ──▶ makePlan(target, delay)  ──▶ PC[]  ＝ 理想計畫（跟現在逐點相同）
S.target2 ──▶ makePlan(target2, delay) ──▶ PC2[] ＝ 保底計畫（同一套關門保護）
                                             │
              coursePayload()：plan 不變，多兩個欄位 target2、plan2
                                             ▼
              Course：plan 不變，多 target2、plan2（沒有就是 null → 行為跟現在一樣）
```

六條不能違反的規則：

1. **沒設保底時，一切跟現在完全相同。** `target2` 是空的 → 不算 `PC2`、course JSON 不含 `target2`／`plan2`、語音與通知列的字一個都不變。這是驗收的第一條。
2. **理想計畫的算法不動。** 把 `buildPlan()`／`buildPlanRows()` 改寫成「不改全域變數、回傳 `{pc, total, adj, bad}`」的純函式 `makePlan(target, delay)`，原本的全域 `PC`、`PLAN_TOTAL`、`PLAN_ADJ`、`PLAN_BAD` 仍然由「理想」那一次的結果填入。改寫前後，6 個賽事包的 `course-<id>.json` 的 `plan` 陣列必須逐點相同（先在 `main` 跑一次自測留下舊檔來比）。
3. **保底不能慢到過不了關門。** 可選的保底上限：`target2 + delay ≤ LIMIT − 6`（跟現有 `PLAN_BAD` 的門檻一致）。保底計畫算完後用同樣的 `checkTight` 檢查：任何一關餘裕不到 2 分鐘 → 準備頁紅字警告「保底 x:xx 在『某關』只剩不到 2 分鐘，請把保底調快」。
   例：京都總時限 360 分、延遲 15 分 → 保底最慢只能到 339 分，選單以 5 分為一格 → **最慢 5:35**。所以京都預設目標 5:30 的人，保底只能選 5:35。這不是 bug，是這場比賽對後段起跑的跑者本來就這麼緊，畫面要把原因講出來：「這場加上起跑延遲 15 分，最慢只能 5:35」。
4. **關門相關的數字不因為有保底而變樂觀。** 關門線、底線照舊。需要「預估還要多久到關門」而沒有即時配速可用時（`GpsService.kmSay()` 的關門餘裕、`checkAlerts()` 的「關門吃緊」），有保底就改用保底計畫的區段時間來估（比較慢 → 比較早提醒）。沒有保底就照舊。
5. **保底線一定不比理想線早。** 兩份計畫各自做關門保護，理論上每一點都是 `PC2[i] ≥ PC[i]`，但不要假設：算完後做 `PC2[i] = max(PC2[i], PC[i])`，自測再檢查一次。
6. **畫面和背景服務的邏輯要一起改。** 語音句子在 `index.html`（`kmSay`、`stopSay`，網頁與示範用）和 `GpsService.java`（APK 用）各有一份，兩邊的字要一樣。

**「目前在區間的哪裡」怎麼判斷**

```

   快 ◀──────────── a ═══════ 區間內 ═══════ b ────────────▶ 慢
       el ≤ a                a < el ≤ b                el > b
       「超前」               「區間內」                 「慢於保底」
       顯示：快 m:ss          顯示：區間內              顯示：慢於保底 m:ss（＝ el − b）
       顏色：綠               顏色：綠                  顏色：黃
```

- 準備頁的標籤用「目標（理想）」「保底」，不要寫成「保底完賽時間」，否則 `select` 會被擠窄（v0.5 的教訓）。
- 首頁卡片的 `5:30–5:35` 是 9 個字元，比現在的 `5:30` 長；那一格是三格並排（`.rspec`），要實測，放不下就把連接號兩邊的字級縮小或換成兩行。
- 通知列標題在窄手機會被系統截斷，所以順序固定為「里程｜區間判定｜關門餘裕」，最重要的在前面。

### ③ PB 與目標建議

**要解決的問題**
新手不知道目標該設多少。現在每場的預設目標是賽事包寫死的（京都 5:30），跟使用者的實力無關。使用者已經有一場完賽成績（日月潭 28.8K），可以用它換算出「這場大概能跑多少」，並直接套用到 ① 和 ②。

**放在哪裡**

1. 準備頁「這一場的參數」卡，目標那一行的正下方：一行建議＋「套用」按鈕。
2. 「全程剖面・分段紀錄・設定」頁（`pgMore`）的個人偏好區：加一塊「我的最佳成績（PB）」，可以看、手動新增、刪除。PB 是個人的，全 App 共用。

```
準備頁（有 PB 時）：
┌────────────────────────────┐
│ 目標（理想）    [ 5:30 ▾ ]   │
│ 保底           [ 5:35 ▾ ]   │
│ 💡 依你的 PB 建議 5:15–5:25  │
│    日月潭 28.8K 3:30:00 換算  │
│    [ 套用 ]  [ 怎麼算的 ▾ ]   │
└────────────────────────────┘

準備頁（沒有 PB 時）：
│ 💡 輸入一筆成績，幫你估這場的  │
│    目標   [ 輸入成績 ]        │

個人偏好區：
┌────────────────────────────┐
│ 我的最佳成績（所有賽事共用）   │
│ 28.8K 3:30:00 日月潭 2026/11 │
│ 10K   1:05:00 手動  2026/9  ✕│
│ [ ＋ 手動新增 ]              │
│ 距離 [半馬 ▾] 時間 [2]:[25]:[00] │
│ 日期 [2026/10 ▾] 路況 [平路 ▾] │
└────────────────────────────┘
```

「怎麼算的」展開後，用三行把算式攤開（使用者喜歡看得懂、能教別人）：

```
① 日月潭 28.8K 3:30:00 → 換算成 42.2K：5:15（距離越長，配速會掉一點）
② 坡度修正：日月潭比京都陡 → 再快約 3%
③ 第一次跑這個距離 → 保守加 3%
```

**PB 從哪裡來**

| 來源 | 做法 |
| --- | --- |
| App 裡的完賽成績 | 每場的 `finished.t`（淨秒數）。**注意：再按一次「開始定位」或「以現在為起跑」就會把 `finished` 清掉**（`prepGo()`、`Android.setStart()`），所以不能只在需要時去讀。做法是「收割」：每次畫首頁或準備頁時，掃一遍所有賽事的 `racePrefs(id).finished`，有非示範（沒有 `demo`）、有 `t` 的就寫進共用的 `pbs`（同一場同一天只留一筆）。不要去改原生的完賽流程。 |
| 手動輸入 | 距離（5K／10K／半馬／全馬／自訂 km）、時間（時:分:秒）、年月、路況（平路 1.00／有起伏 1.03／山路 1.08） |

**計算規則**

符號：來源成績 `T1`（分）、來源距離 `D1`（km）、來源難度 `F1`；目標賽事距離 `D2`、難度 `F2`。

第 1 步：難度係數 `F`（坡度讓這條路線比平路慢多少）。直接用引擎自己的坡度模型，這樣「建議」和「配速計畫」的假設一致：

```
對路線上每一小段算坡度 g（%，限制在 −8 到 +12）：
  上坡 w ＝ 1 + 0.04 × g        下坡 w ＝ 1 + 0.014 × g      ← 就是 weight() 裡的那兩個數
F ＝ 所有小段 w 的平均（只算坡度，不含擁擠與疲勞）
```

用現在的賽事包算出來的值（自測要驗，容許 ±0.002）：

| 賽事 | F | 總爬升（首頁卡片的算法） |
| --- | --- | --- |
| 東京 | 1.002 | 51 m |
| 紐約 | 1.011 | 188 m |
| 京都 | 1.013 | 187 m |
| 日月潭 28.8K | 1.042 | 414 m |
| 陽明山全馬 | 1.073 | 1151 m |
| 陽明山半馬 | 1.081 | 629 m |

手動輸入的 PB 沒有路線，用使用者選的路況（1.00／1.03／1.08）。

第 2 步：Riegel 公式換算距離，再換回目標路線的難度。

```
平路等效    T1f ＝ T1 / F1
Riegel      T2f ＝ T1f × (D2 / D1)^e
換到目標路線 T2  ＝ T2f × F2

理想用 e ＝ 1.06（Riegel 原始值）
保底用 e ＝ 1.12（休閒跑者拉長距離時，實際掉速比 1.06 多）
D2 ≤ D1 時（換算到一樣或更短的距離）兩者都用 1.06
```

第 3 步：新手修正 `n`。如果 `D2 > 所有 PB 中最長距離 × 1.2`（也就是第一次跑這麼長），理想和保底都再 × 1.03；否則 × 1.00。

第 4 步：取整與安全上限。

```
理想 ＝ 四捨五入到 5 分
保底 ＝ 無條件進位到 5 分，而且至少比理想多 10 分
安全上限 maxSafe ＝ floor5(LIMIT − 6 − delay)      ← 跟 ② 的保底上限同一條規則
```

**數字範例 1（正常）**：日月潭 28.8K 完賽 3:30:00，換算京都。

```
T1＝210 分，D1＝28.8，F1＝1.042；D2＝42.195，F2＝1.013
距離倍率 (42.195 / 28.8)^1.06 ＝ 1.4991；^1.12 ＝ 1.5338
理想：210 / 1.042 × 1.4991 × 1.013 ＝ 306.1 → 新手 ×1.03 ＝ 315.3 → 5:15
保底：210 / 1.042 × 1.5338 × 1.013 ＝ 313.2 → 新手 ×1.03 ＝ 322.6 → 進位 5:25
maxSafe ＝ floor5(360 − 6 − 15) ＝ 5:35 → 兩個都在安全範圍內
顯示：「依你的 PB 建議 5:15–5:25」
```

**數字範例 2（撞到關門）**：同一場成績是 3:45:00。

```
理想：225 / 1.042 × 1.4991 × 1.013 × 1.03 ＝ 337.8 → 5:40
保底：225 / 1.042 × 1.5338 × 1.013 × 1.03 ＝ 345.6 → 5:50
maxSafe ＝ 5:35 → 理想和保底都比安全上限慢
```

這時候不能把 5:40–5:50 套進去（加上起跑延遲會過不了終點關門）。畫面改成黃色提醒，把實話講清楚：

```
│ ⚠ 依你的 PB 換算約 5:40–5:50， │
│   但這場加上起跑延遲 15 分，    │
│   最慢只能 5:35。              │
│   完賽有壓力：確認起跑分區能不能│
│   往前，備賽期把長跑練足。      │
│   [ 套用 5:35 ]                │
```

「套用」的規則：`target ＝ min(理想, maxSafe)`；`target2 ＝ min(保底, maxSafe)`，如果結果沒有比 `target` 大就不設保底。

**選哪一筆 PB 來算**：對每一筆 PB 都算出這場的「理想」，取**最近 12 個月內**最快的那一筆；12 個月內沒有就用最新的一筆，並標「成績較舊，僅供參考」。可信度提示：`D2 / D1 > 4.5`（例如用 5K 估全馬）標「距離差太多，估得不準」；`D1 < 5 km` 的成績不拿來估。

**一鍵套用會做什麼**

```
[ 套用 ] ──▶ target ＝ 建議的理想 ──▶ replan()：重算配速計畫、關門保護、pushCourse()
        ├─▶ target2 ＝ 建議的保底（② 還沒做完時，略過這一步）
        └─▶ ① 的課表：Lmax 依新目標重算，卡片顯示「已依新目標更新」
```

- 目標選單（`#target`）現在只有賽事包列的幾個選項（京都是 4:30–5:45、每 15 分一格）。建議值是 5 分一格，可能不在選單裡。做法：套用時如果選單沒有這個值，就插入一個選項（標示「5:15（PB 建議）」）並依時間排序；`racePrefs` 讀回的 `target` 不在選單裡時，開頁面也要插入，否則選單會顯示成別的值。
- 套用前後都顯示在同一張卡上，並提供「復原」（記住套用前的 `target`／`target2`，本次停留在頁面期間有效）。
- 套用不會自動發生。App 只建議，決定權在使用者。

**儲存欄位**

| 欄位 | 範圍 | 型別 | 內容 |
| --- | --- | --- | --- |
| `pbs` | **共用**（`pref`） | JSON 字串（陣列） | `[{"k":"sunmoonlake-29k-2026@2026-11-01","src":"race","rid":"sunmoonlake-29k-2026","name":"日月潭 29K","d":28800,"t":12600,"date":"2026-11-01","f":1.042}, {"k":"m1","src":"manual","name":"手動","d":10000,"t":3900,"date":"2026-09","f":1.0}]` |

- `d` 公尺、`t` 秒、`f` 難度係數（收割時當場用該賽事路線算好存起來，之後賽事包改版也不影響舊成績）。
- `pbs` 要加進 `index.html` 與 `MainActivity.java` 兩邊的 `SHARED`，並在 `racePrefs()` 網頁分支與 `getPrefs()` 讀出來（4 個地方，見「儲存規則」）。
- 從賽事收割來的 PB 可以刪（刪了之後，同一筆 `k` 記在 `pbs` 的「已刪除」清單裡，避免下次又被收割回來；可以用 `{"k":…,"del":1}` 表示）。
- 以後 PR #6 合併了，訓練紀錄裡 `kind==='race'` 的活動也可以當 PB 來源，但那是之後的事，這次不要做。

**驗收條件**

1. 沒有任何 PB：準備頁顯示「輸入一筆成績」引導，其他功能不變。
2. 手動新增「28.8 km、3:30:00、路況選有起伏」→ 用 F1＝1.03 算；改用收割的日月潭成績（F1＝1.042）→ 京都顯示「建議 5:15–5:25」。
3. 同一筆成績在東京（時限 7:00、F＝1.002）顯示的建議比京都快（因為更平），而且不會出現關門警告。
4. 範例 2 的成績在京都顯示黃色提醒與「套用 5:35」。
5. 按「套用」→ 目標選單變成建議值、計畫表與關門餘裕跟著更新；回首頁再進來，值還在；另一場賽事的目標沒有被改到。
6. 日月潭示範模式跑完（`FIN.demo`）不會被收割成 PB。
7. 在日月潭完賽後，再按一次日月潭的「開始定位」（`finished` 被清掉）→ PB 列表裡那筆成績還在。
8. APK 與網頁版都要驗 5 與 7（最容易漏的是 `getPrefs()` 沒把 `pbs` 讀出來）。

**要加的自測**

- 純計算：
  - `PREP.riegel(210, 28.8, 42.195, 1.06)` ≈ 314.8；`1.12` ≈ 322.1（容許 ±0.2）。
  - `PREP.difficulty(race)` 對 6 個賽事包等於上表（±0.002）。
  - `PREP.suggest(...)` 範例 1 → `{ideal:315, floor:325, capped:false}`；範例 2 → `{ideal:340, floor:350, maxSafe:335, capped:true}`。
  - 邊界：`D2 ≤ D1`、只有一筆很舊的 PB、`D1 < 5`、`D2/D1 > 4.5` 都不產生 `NaN`，並回傳對應的提示旗標。
- 畫面：自測專用參數 `&pb=28800,12600,1.042`（距離公尺、秒、難度）→ 開京都準備頁，檢查出現「5:15–5:25」；按「套用」後 `#target` 的值是 315、計畫表總時間是 5:15、畫面沒有 `NaN`。300 與 390 各量一次 `overflow`，「怎麼算的」展開後再量一次。
- 收割：在自測裡直接呼叫收割函式，餵一個假的 `finished`（一筆正常、一筆 `demo`），檢查只收到一筆。

**300 px 注意事項**

- 建議那一行可能很長（「依你的 PB 建議 5:15–5:25」＋來源），固定拆成兩行：第一行結論、第二行小字來源。
- 手動輸入的「時:分:秒」用三個窄的數字輸入框（`inputmode="numeric"`，每個約 3 個字寬），不要用一個長文字框；距離用下拉，自訂時才出現數字框。
- PB 列表每列：距離、時間、來源、刪除鈕四樣。300 px 時來源與日期換到第二行小字。

## 不建議做的事

| 不做 | 原因 |
| --- | --- |
| AI 教練（在 App 裡接語言模型給建議） | App 必須離線可用；比賽現場沒有網路時不能少一塊功能。建議要可預測、可驗算，使用者才能教別人「這個數字怎麼來的」。固定規則＋把算式攤開就夠了 |
| 直接連 Garmin／Strava API | 要登入授權、要網路、要保管金鑰，對方改版就壞；比賽日多一個可能出錯的東西。匯入 CSV 檔已經能拿到需要的資料（PR #6） |

| 為了新功能去動 GPS 對位、完賽判定、關門計算 | 這三樣是比賽日的核心，已經有自測保護，沒有明確的 bug 不要碰 |

| 日月潭計畫總時間略少於目標 | 目標 255 分，手調 `rows` 模型算出 253.4 分（自測容許 3 分） | 不影響比賽；要修就把 rows 等比例縮放到目標 |
| `README.md` 過時 | 架構圖只畫兩個賽事包，沒提節拍器 | 有空時同步本檔 |

比賽相關的硬規則：比賽日只用 APK；網頁版鎖屏後瀏覽器會停，不能拿來比賽。

## 新增賽事：只要說「新增 XXX」

以後要加一場比賽，在專案裡只打「新增 XXX」（例如「新增 2027 臺北馬拉松」）。Claude 會自己查資料、補齊所有要留意的地方，只有真的需要使用者決定的事才會問。

```markdown
## 新增賽事規則（Run-Navigator）
當我只說「新增 XXX」（XXX＝賽事名稱，可能含年份或距離），照下面流程做，不要等我補充細節。

### 1. 先自己查（官方優先，再用真實跑者紀錄多方比對，每項標來源與可信度）
- 日期、鳴槍時間、時區、距離組別、起點／終點、總時限
- 接下來幾年（至少 3 屆）的報名期間與比賽日期：已公布的附官方來源；沒公布的照往年慣例推估並標「預估」、寫推估依據（寫進 race.json 的 schedule）
- 關門點：名稱、公里數、關門時刻（以鳴槍計還是個人計）
- 補給站：水／運動飲料／食物／鹽的公里數與品項；廁所
- 路線檔：官方 GPX > RideWithGPS／Strava／Garmin／ibuki 等公開路線；找不到就請我提供（My Maps KML 或 GPX）
- 地形：每段爬升與下降、最高點、陡坡、未鋪裝或狹窄路段、風大路段
- 路線結構：折返段（去回程只隔一條路）、繞圈（同一段跑兩次以上）、多組別共用路段與分岔口（例：日月潭 29K 在頭社右轉、42K 左轉）
- 起跑：分區、整隊截止、各區過線延遲實測、配速員時間與分區
- 規則：是否禁止耳機或手機（影響語音提醒的用法）、寄物、退賽交通
- 天氣：近 3 年比賽日起跑與終點氣溫、降雨
- 報到時間地點、要帶的證件；海外賽要注意現金、時差、手機漫遊

### 2. 只問我這些（一次問完，用選項）
- 報哪個距離組別（有多組時）
- 目標完賽時間；不確定就依我最近一場成績換算建議
- 起跑分區（不知道就用預估延遲，之後可改）
- 查不到路線檔時，請我提供檔案
- 資料互相矛盾、會影響配速或關門判斷的地方

### 3. 做成賽事包（不能影響其他賽事）
- 新資料夾 app/src/main/assets/races/<id>/：race.json（照現有賽事包的欄位）、route.gpx、route.json、map.png
- id 是存檔的鑰匙，定了就不改；每年通用的賽事 id 不帶年份（例：tokyo-marathon）
- python3 tools/build_route.py app/src/main/assets/races/<id>   ← 由 route.gpx 產生 route.json（縮放到官方距離）
- python3 tools/build_races.py                                   ← 檢查所有賽事包並重新產生 races.js（一定要跑，races.js 不要手改）
- 路線與官方地標比對誤差（目標 ±0.3 km 內，超過要說明）
- 地標、區段（A 點→B 點、地形、策略）、關門、水站、能量膠計畫、配速模型（預設 grade；關門保護的餘裕寫在 plan.cut_buffer_min）
- 離線地圖 map.png（參考 tools/maps/ 的腳本）、語音念法（時間念成「幾點幾分」、去掉括號）
- 折返或繞圈路段：確認 GPS 對位不會跳到另一條腿
- 時區以賽事當地為準，畫面標明
- 首頁卡片：在 index.html 的 ITEM_ICONS（圖示）、RACE_STYLE（地點、顏色、一句話路線）、RACE_CATS（組別）各補一筆

### 4. 驗證與發佈
- python3 tools/build_races.py --check 與 node tools/selftest.js 全過：新賽事示範跑完全程、每 1K 與地標語音正確、關門餘裕合理、終點自動完賽、300 px 不破版
- 既有賽事包會一起重跑，確認沒被影響
- app/build.gradle 的 versionCode、versionName +1；開 PR；確認 Actions 四個步驟都過（含 JVM 對位模擬與編 APK）
- 合併到 main 由我決定
- 官方參賽指南還沒公布的話，設排程在賽前定期檢查並自動更新

### 5. 回報我
- 一張表：查到的資料、來源、可信度、還缺什麼
- 這場最需要注意的 3 件事（例：前段關門最緊、某處分岔口、禁止耳機）
- 測試版 APK 下載位置（PR 的 Actions → Artifacts），以及手機上要確認的設定
```

要調整這份清單（例如多查一項），直接改上面的區塊，再同步貼回專案指示即可。
